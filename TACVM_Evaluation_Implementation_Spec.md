# TACVM Evaluation Harness — Complete Implementation Specification

**Purpose:** This document is an implementation contract for Cursor. Implement the full TACVM evaluation harness described below without changing TACVM protocol semantics. Reuse the existing scripts and verifier wherever possible, add structured instrumentation, and produce reproducible raw data, summaries, and paper-ready plots.

**Scope:** The harness must evaluate: (1) multi-party trust establishment for the Operation CVM, (2) policy-processing scalability, (3) Workload CVM provisioning/boot/authentication/live-binding, (4) concurrent Workload CVM authentication, (5) representative workload admission, (6) steady-state Redis and ResNet-50 performance, and (7) security validation.

---

## 1. Existing implementation assumptions that must be preserved

The current code/testbed already has the following behavior. Do not regress it.

- A fleet of **16 Workload CVMs** is available.
- Each guest launcher uses globally unique client IDs derived from `CVM_INSTANCE_ID`, e.g.:
  - `cvm_01_client_01`
  - `cvm_01_client_02`
  - `cvm_16_client_02`
- Existing scripts include at least:
  - `launch-client.sh`
  - `cvm-fleet-test.sh`
  - `quote-verify-run.sh` (or equivalent participant attestation driver)
- The native verifier currently runs as `/root/vm-verifier/policy_server` and listens on `0.0.0.0:50051` in the current test setup.
- `policy_server` is a multi-threaded gRPC service.
- Two concurrency fixes already exist and must remain enabled:
  1. `state_mutex_` protects shared access to `pending_challenges_` and `sessions_`.
  2. A process-wide appraisal mutex serializes the DCAP QVL/appraisal sequence.
- Current smoke tests have already shown:
  - participant RA succeeds up to 32 participants;
  - policy reconciliation succeeds up to 32 participants;
  - the verifier can accept 16 CVMs × 1 client and 16 CVMs × 2 clients without failure after the fixes.

**Important:** Those existing measurements are smoke-test/reference data only. Do not copy them into final evaluation result files. Official results must be regenerated by the new harness with a run ID, structured metrics, clean logs, and the methodology below.

## 2. Evaluation questions and final paper outputs

The implementation must support the following final evaluation structure.

### Q1 — Multi-party trust establishment
How much time does TACVM require to establish an Operation CVM trusted control plane as the number of participants increases?

**Paper output:** Figure 6(a): trust-establishment latency versus participant count, with phase breakdown.

### Q2 — Policy-processing scalability
How does policy verification/join/candidate construction scale as the policy size increases?

**Paper output:** Figure 6(b): policy-processing latency versus rules per participant.

### Q3 — Workload CVM authentication
How much time does TACVM require to provision, boot, authenticate, and establish a live binding `B_w` for a Workload CVM?

**Paper output:** Figure 7(a): single Workload CVM end-to-end latency and breakdown.

### Q4 — Concurrent Workload CVM authentication
How does the Operation CVM authentication service scale when multiple Workload CVMs are authenticated concurrently?

**Paper output:** Figure 7(b): authentication throughput versus concurrent Workload CVMs.

### Q5 — Representative workload admission
What is the end-to-end cost of applying the established trust chain to one representative `admit` operation?

**Paper output:** Figure 8(a): TACVM versus TDX-Direct end-to-end admission latency.

### Q6 — Steady-state application overhead
After admission completes, does TACVM remain on the application data path and reduce steady-state performance?

**Paper output:** Figure 8(b): Redis and ResNet-50 normalized throughput, TACVM versus TDX-Direct.

### Q7 — Security validation
Do the implemented enforcement points reject stale, replayed, mismatched, or unauthorized states/requests as designed?

**Paper output:** one security-validation table.

## 5. Run identity, reproducibility, and manifest

Every invocation of any official experiment must create or reuse a unique `run_id`:

```text
YYYYMMDD-HHMMSS-<git_short_sha>
```

Every `results/<run_id>/manifest.json` must record at least:

- git commit SHA and dirty/clean state;
- experiment name;
- command line;
- config snapshot;
- host CPU model, physical/logical CPU count;
- memory size;
- kernel version;
- QEMU/KVM version;
- TDX module/firmware versions if available;
- DCAP/QVL/QGS versions if available;
- Operation CVM vCPU/memory;
- Workload CVM vCPU/memory;
- verifier binary SHA256;
- relevant workload binary/image/model hashes;
- start/end wall-clock time for auditing only;
- whether quote collateral is warm or cold;
- list of participating CVM IDs and client IDs.

Official latency calculations must use monotonic clocks, not wall clock.

---

## 6. Timing rules — mandatory

### 6.1 Use monotonic clocks

- C/C++: `clock_gettime(CLOCK_MONOTONIC_RAW, ...)` where practical.
- Python: `time.monotonic_ns()`.

### 6.2 Never subtract timestamps from different machines/process clock domains

Do **not** compute a duration as `guest_timestamp - host_timestamp` or `CVM-A timestamp - CVM-B timestamp`.

Instead:

- measure end-to-end duration at the controller from one controller-side start/end pair; and/or
- measure a local phase duration from start/end timestamps emitted by the same process.

Phase durations may be summed for presentation, but preserve the independently measured end-to-end total as a consistency check.

### 6.3 Structured metric events

Production components that need instrumentation should emit one-line JSON events, for example:

```json
{"run_id":"...","event":"QUOTE_VERIFY_END","entity":"cvm_03","client_id":"cvm_03_client_01","ts_ns":123456789,"duration_us":17120,"status":"success"}
```

Required fields:

```text
run_id
event
ts_ns
status
```

Add entity-specific fields as needed. Logs must remain human-readable, but JSONL metrics must be machine-parseable.

## 7. Common execution methodology

### 7.1 Latency experiments

Default per configuration:

```text
5 warm-up runs
30 measured runs
3 independent sessions
```

The harness must permit changing these values in `eval.yaml`.

A session must restart the relevant client state and clear experiment-specific logs. Where the experiment is explicitly measuring cold boot, restart the corresponding CVM as defined below.

### 7.2 Steady-state workload experiments

Per configuration:

```text
30 s warm-up
120 s measured interval
5 internal windows (for diagnostics)
3 independent sessions
```

### 7.3 Quote collateral

Primary paper measurements use **warm DCAP collateral** to avoid Internet/PCCS cache behavior dominating TACVM mechanism cost. Record collateral state in the manifest.

### 7.4 Configuration isolation

For TACVM and baseline runs, keep constant:

- physical host;
- VM vCPU and memory;
- VM image where applicable;
- kernel and runtime versions;
- network path;
- workload artifact/model;
- benchmark load parameters.

### 7.5 Order control

Within each independent session, randomize the order of scale points with the configured deterministic seed to reduce thermal/time drift. Record actual execution order.

## 8. Preflight validation — must pass before any official measurement

Implement `evaluation/bin/eval-preflight`.

It must fail fast if any of the following checks fails:

1. All required hosts/CVMs are reachable.
2. All client IDs are globally unique.
3. The native verifier is listening on the configured port.
4. No stale alternative verifier process/container is serving the same endpoint.
5. `policy_server` process is alive before the run.
6. Required binaries/scripts exist.
7. Required model/artifact files exist and hashes are recorded.
8. Disk space is sufficient for logs/results.
9. No stale `run_id` directory would be overwritten.
10. Time measurement APIs are available.
11. The expected TDX/DCAP path passes one smoke attestation.
12. Current global-client-ID logic is enabled.
13. Negative-test mode is OFF for performance experiments.

After each performance run, assert:

- expected number of successes occurred;
- no unexpected `VERIFY_RESULT=FAILED` occurred;
- no segmentation fault appeared;
- verifier is still alive and listening;
- no SSH/fleet orchestration failure occurred.

If any assertion fails, mark that run invalid and save all logs. Do not silently retry and overwrite evidence.

# Experiment E1 — Multi-party Operation CVM Trust Establishment

## 9. Goal

Measure the full cost of establishing the Operation CVM trusted control plane as participant count increases.

Scale:

```text
N = 2, 4, 8, 16, 32
```

The official metric is not merely quote verification. It is the full path:

```text
Operation CVM launch
→ measured boot / integrity setup
→ TACVM control service ready
→ all required participants authenticate the Operation CVM
→ participant policy proposals are verified/joined
→ candidate policy is confirmed
→ policy_active = true
```

## 10. E1 timing boundaries

Collect these durations:

### `boot_ms`

Controller-side interval:

```text
T0: Operation CVM launch command/request issued
T1: Operation CVM TACVM service is ready to accept participant authentication
```

This includes the Operation CVM boot path relevant to TACVM, including measured boot/dm-verity/service startup. Do not include unrelated pre-experiment host provisioning.

### `participant_auth_ms`

Measure from the moment the participant-authentication batch starts until all `N` required participants are authenticated/registered for this run.

The production service should emit an explicit `ALL_PARTICIPANTS_AUTHENTICATED` event carrying `N` and `run_id`.

### `policy_establishment_ms`

Measure from the first policy-establishment action after authentication completion until `policy_active=true`.

Internally also record:

```text
proposal_verify_ms
restrictive_join_ms
candidate_construct_ms
participant_confirm_ms
```

### `total_ms`

Controller-side full interval:

```text
Operation CVM launch request → policy_active observed
```

Do not calculate `total_ms` only as a sum. Measure it independently and also save:

```text
phase_sum_ms = boot_ms + participant_auth_ms + policy_establishment_ms
phase_gap_ms = total_ms - phase_sum_ms
```

If absolute `phase_gap_ms` exceeds 5% of `total_ms`, flag the run for investigation.

## 11. E1 output schema

`raw/e1_trust_establishment.csv`

```text
run_id,session_id,run_index,N,warmup,status,
boot_ms,participant_auth_ms,policy_establishment_ms,total_ms,
proposal_verify_ms,restrictive_join_ms,candidate_construct_ms,participant_confirm_ms,
phase_sum_ms,phase_gap_ms
```

## 12. E1 implementation requirements

- Reuse current participant-attestation and reconciliation logic; do not create a second protocol implementation.
- Wrap/extend `quote-verify-run.sh` only as needed to pass `run_id`, emit structured results, and suppress historical-log ambiguity.
- Rotate/truncate per-run server logs or tag every log/event with `run_id`.
- Participant IDs must be deterministic and unique.
- The harness must detect whether current participant authentication is serialized. Do not automatically parallelize it for the paper unless the TACVM design/implementation itself is intentionally changed. Measure the implementation as it exists.

## 13. Figure 6(a)

Generate a stacked bar chart:

- X: participant count `N`.
- Y: latency in ms.
- Stacks:
  - Operation CVM boot
  - participant authentication
  - policy establishment
- Error bar: 95% confidence interval of total latency.

Also generate a CSV summary containing mean, median, p95, standard deviation, and CI.

## 14. Goal

Isolate Open Policy Parser / reconciliation cost from remote attestation and network round trips.

Fixed:

```text

```

Scale:

```text
P = 10, 100, 1000 rules per participant
```

Optionally support `5000` via config, but do not require it for the first official run.

## 15. Policy fixture generator

Implement `policy/generate_policy_fixture.py`.

Requirements:

- deterministic output from a supplied random seed;
- syntactically valid TACVM policy proposals;
- semantically non-conflicting by default so all scale points produce a valid candidate policy;
- exactly `P` logical rules/entries per participant;
- stable rule shape across scale points so the independent variable is rule count, not rule complexity;
- unique object/rule IDs;
- valid signatures using the normal proposal-signing path;

Also support an optional `--conflict` mode for security tests, but not for E2 performance results.

```text

candidate_construct_ms
policy_processing_total_ms
```

Where:

```text
policy_processing_total_ms = proposal_verify_ms + restrictive_join_ms + candidate_construct_ms
```

Also independently measure parser-stage total if possible and check for instrumentation gaps.

# Experiment E3 — Single Workload CVM Provisioning, Boot, Authentication, and Live Binding

## 19. Goal

Measure the complete Workload CVM trust-extension path for one instance.

The experiment includes **provisioning**. Do not remove it.

Full path:

```text
provisioning request
→ Workload CVM instance/resource created
→ VM boot starts
→ measured boot / Trusted Service startup
→ fresh TACVM launch context is incorporated
→ Quote is generated
→ Operation CVM verifies evidence
→ authenticated control channel is established
→ B_w is established
```

## 20. Provisioning definition

Cursor must first discover and reuse the actual VM lifecycle primitive used by the repository/testbed. Do not invent a second VM manager.

Implement a `VMProvider` abstraction in `evaluation/lib/vm.py` with these operations:

```python
provision(instance_id) -> ProvisionResult
start(instance_id)
wait_trusted_service_ready(instance_id)
stop(instance_id)
destroy(instance_id)
reset(instance_id)
```

For the current local testbed, `provision()` must wrap the existing mechanism that prepares/creates the Workload CVM instance (disk/config/resource definition). If the current 16 VMs are pre-created, add an **ephemeral clone/test-instance path** based on the same golden Workload CVM image so provisioning is measurable without destroying the fleet.

Do not define provisioning as a dummy sleep or `0 ms`. If no reproducible provisioning primitive exists, fail E3 with a clear `PROVISIONING_UNAVAILABLE` status until one is implemented.

## 21. E3 phases

Record:

### `provision_ms`

```text
provision() invocation → instance resources/configuration created and ready to start
```

### `boot_ms`

```text
VM start invocation → Trusted Service ready for TACVM authentication
```

### `quote_gen_ms`

Measured locally inside the Workload CVM from Quote generation start to Quote ready.

### `quote_verify_ms`

Measured locally inside Operation CVM/verifier from evidence verification start to result.

### `appraisal_wait_ms` and `appraisal_service_ms`

Because the current verifier uses a process-wide appraisal mutex, instrument separately:

```text
appraisal_wait_ms: time waiting to acquire the appraisal mutex
appraisal_service_ms: time holding the appraisal mutex while doing QVL/appraisal
```

These values are diagnostic and do not need a main paper plot, but they are mandatory raw metrics for interpreting saturation.

### `channel_binding_ms`

Authenticated channel/live-binding work after evidence acceptance until `B_w` is committed.

### `auth_binding_ms`

Overall authentication/binding portion after Trusted Service readiness:

```text
Trusted Service ready / authentication triggered → B_w ready
```

### `total_ms`

Controller-side:

```text
provisioning request → B_w ready
```

## 22. TDX-Direct-Launch baseline

Implement a performance-reference mode named `tdx-direct-launch`.

Requirements:

- same Workload CVM image/hardware resources;
- same provisioning and VM boot mechanism;
- same TDX Quote generation path;
- same DCAP/QVL verifier stack where possible;
- exclude TACVM-specific policy-controlled live-binding logic (`B_w`) and TACVM-specific launch-context/channel-policy checks that are not required by plain direct attestation.

This is a **performance reference, not a security-equivalent baseline**. The code and generated captions must never label it security-equivalent.

If an existing direct-attestation client exists, reuse it. Otherwise implement the minimum direct-attestation path as a clearly separate baseline adapter without altering TACVM production code.

```text
run_id,session_id,run_index,system,warmup,status,
provision_ms,boot_ms,quote_gen_ms,quote_verify_ms,
appraisal_wait_ms,appraisal_service_ms,channel_binding_ms,auth_binding_ms,total_ms
```

Where `system` is one of:


# Experiment E4 — Concurrent Workload CVM Authentication

## 25. Goal

Measure authentication scalability when multiple Workload CVMs are processed concurrently.

Primary scale:

```text
M = 1, 2, 4, 8, 16
```

Support `M=24` only when the testbed has enough reproducible Workload CVM instances/resources. Since the current fleet has 16 CVMs, `M=16` is the required maximum for the native fleet unless ephemeral instances are added.

## 26. E4 setup

For the authentication-throughput experiment, provisioning may happen before the synchronized authentication release if necessary to isolate the authentication service, **but E3 remains the full provisioning-to-binding experiment**.

Required E4 procedure:

1. Prepare `M` Workload CVMs in a deterministic ready-to-authenticate state.
2. Give every CVM a unique `CVM_INSTANCE_ID` and unique client ID.
3. Create fresh launch/authentication state; no stale challenge/session may be reused.
4. Synchronize clients on a barrier.
5. Release all `M` authentication attempts as simultaneously as the current fleet tooling allows.
6. Wait until all `M` results are complete.
7. Verify the verifier process is still alive afterward.

The existing `cvm-fleet-test.sh` should be extended rather than replaced if it already provides the synchronized release mechanism.

## 27. E4 metrics

Controller-side:

```text
batch_start_ns
batch_end_ns
batch_time_s
successful_cvms
failed_cvms
```

Compute:

```text
auth_throughput_cvms_s = M / batch_time_s
```

Per CVM/client:

```text
elapsed_ms
quote_verify_ms
appraisal_wait_ms
appraisal_service_ms
```

Aggregate:

```text
median_latency_ms
p95_latency_ms
max_latency_ms
```

Also preserve `fleet_first_message_spread_ms` (or equivalent barrier-release skew) as a diagnostic field. This is not a primary paper metric, but high release skew must be visible because it can invalidate concurrency interpretation.

## 28. E4 baseline

Run the same scale points with `tdx-direct-launch` authentication mode where practical. If the baseline cannot share the exact fleet launcher, implement a parallel direct-attestation fleet adapter with identical barrier/release semantics.

## 29. E4 output

`raw/e4_workload_auth_concurrent.csv`

One row per batch:

```text
run_id,session_id,run_index,system,M,warmup,status,
batch_time_s,throughput_cvms_s,median_latency_ms,p95_latency_ms,max_latency_ms,
release_spread_ms,successful_cvms,failed_cvms
```

Save a second detail file with one row per CVM/client:

`raw/e4_workload_auth_concurrent_clients.csv`

- Y: authentication throughput (CVMs/s).

# Experiment E5 — Representative Workload Admission

## 31. Goal

Measure one representative `admit` operation because it exercises the complete runtime control path. Do not build a CRUD request generator and do not turn `update/stop/delete` into separate main experiments.

Precondition for each measured run:

```text
Operation CVM trusted control plane already active
Workload CVM already authenticated
B_w already valid
workload state = absent
artifact not yet admitted for the measured operation
```

Path:

```text
signed admit request
→ Operation CVM authenticates requester
→ policy authorization
→ live-binding validation
→ conditional secret/key release
→ command dispatch
→ Trusted Service verifies current prior state
→ Trusted Service verifies referenced artifact
→ workload starts
→ application reports READY
```

## 32. Artifact

Use one fixed encrypted artifact for all official E5 runs. Initial target size:

```text
100 MiB
```

The exact artifact may be a representative TACVM workload bundle. Record SHA256 and exact byte size.

Do not regenerate a different random artifact for each run; that would add a confounder.

## 33. E5 timing boundary

Primary metric:

```text
T0: admission/deployment request submitted
T1: application reports READY using the same readiness predicate in TACVM and baseline
end_to_end_admission_ms = T1 - T0
```

Add local instrumentation for:

```text
authorization_ms
secret_release_ms
dispatch_ms
artifact_transfer_ms
trusted_service_verify_ms
application_startup_ms
```

The exact phase sum may not equal the controller-side total because some activities can overlap. Do not force-add overlapping phases into a fake total.

## 34. TDX-Direct baseline

Implement `tdx-direct` as a performance reference:

- same already-running Workload CVM resources;
- same artifact;
- same transfer path as much as possible;
- same application startup/readiness condition;
- no TACVM Operation CVM authorization, TACVM Key Vault release, TACVM Dispatcher, or TACVM Trusted Service policy-control path.

Again, mark it as a performance reference, not security-equivalent.

## 35. E5 output

`raw/e5_workload_admission.csv`

```text
run_id,session_id,run_index,system,warmup,status,
artifact_bytes,end_to_end_admission_ms,
authorization_ms,secret_release_ms,dispatch_ms,artifact_transfer_ms,
trusted_service_verify_ms,application_startup_ms
```

## 36. Figure 8(a)

Primary version: two bars with 95% CI:

```text
TDX-Direct
TACVM
```

Y: end-to-end admission latency (ms).

Only use a stacked breakdown if the data show a meaningful explanation. The plotting script should support both `--mode total` and `--mode breakdown`, with `total` as the default paper output.

# Experiment E7 — Security Validation

## 42. Goal

Automate negative tests that exercise the design's actual rejection points. This experiment produces a table, not a performance chart.

Run destructive image modifications only on ephemeral copies/snapshots. Never corrupt the golden fleet image.

Each case must record:

```text
case_id
setup
expected_enforcement_point
observed_enforcement_point
expected_result
observed_result
B_w_created_or_valid
secret_released
workload_state_changed
server_alive_after_test
log_reference
PASS/FAIL
```

## 43. Security cases

### S1 — Modified Operation CVM root filesystem

Modify a test copy of a TACVM service/configuration protected by the Operation CVM integrity chain.

Expected:

```text
integrity/attestation failure
no workload-control authority
policy must not become active
```

### S2 — Invalid Operation CVM attestation evidence

Inject one at a time:

```text
wrong nonce
wrong REPORTDATA/channel-key binding
wrong expected measurement/manifest digest
invalid signature/evidence where supported by the test shim
```

Expected:

```text
participant rejects
participant policy registration/enrollment does not complete
```

### S3 — Replay Workload CVM launch context

Replay an already consumed/stale launch context.

Expected:

```text
no new B_w
no protected workload/secret release
```

### S4 — Wrong Workload CVM measurement

Modify a test Workload CVM copy so one expected boot/integrity measurement differs.

Expected:

```text
Operation CVM rejects evidence
B_w is not established
```

### S5 — Invalid or stale workload request

Cover at least:

```text
invalid participant signature
wrong active-policy hash/version
replayed operation/request ID
operation not authorized by active policy
```

Expected:

```text
Dispatcher/authorization stage rejects
state unchanged
no new secret release
```

### S6 — Wrong prior workload state

Authorize a transition based on prior state `S_i`, then arrange actual state so `S_actual != S_i` before Trusted Service execution.

Expected:

```text
Trusted Service rejects immediately before execution
state remains unchanged by the rejected transition
```

### S7 — Wrong artifact digest

Reference digest `h_a` in the request but provide a different artifact.

Expected:

```text
Trusted Service rejects artifact
transition not applied
```

### S8 — Workload CVM restart or authenticated-channel loss

Establish `B_w`, then restart the Workload CVM or deliberately tear down the authenticated control channel.

Expected:

```text
old B_w invalidated
old binding cannot authorize a new transition
re-authentication required
```

# 46. Concurrency instrumentation — mandatory because of current mutexes

The current correctness fix serializes DCAP QVL/appraisal with a process-wide mutex. Keep the mutex unless thread safety is proven and a separate change is intentionally reviewed.

For every verification request record:

This allows later interpretation of Figure 7(b). If throughput saturates at high `M`, the analysis can determine whether the bottleneck is appraisal serialization rather than VM/network behavior.

# 51. Acceptance criteria for Cursor implementation

The implementation is complete only when all of the following pass.

## Functional acceptance

- `eval-preflight` passes on the intended testbed.
- Smoke mode can execute E1–E7 with reduced sizes.
- Every experiment creates structured raw data and logs under one run directory.
- Global client IDs remain unique across all CVMs.
- No historical log entry can be mistaken for the current run because every parsed metric is scoped by `run_id`.
- Native verifier remains alive after concurrency smoke tests.
- Negative tests reject at the intended enforcement point.

## Measurement acceptance

- No cross-machine timestamp subtraction exists in analysis code.
- E1 measures Operation CVM boot, participant authentication, policy establishment, and independent end-to-end total.
- E2 varies rules per participant while keeping participant count fixed.
- E3 includes provisioning, boot, attestation, and `B_w` establishment.
- E4 reports batch makespan, throughput, per-CVM latency, and appraisal mutex waiting time.
- E5 measures request-to-READY admission latency.
- E6 reports absolute and normalized Redis/ResNet performance.
- E7 emits a machine-readable security table.

## Reproducibility acceptance

- Git SHA/config/hardware/software versions are captured.
- Every fixture/model/artifact hash is captured.
- Randomized execution order is seeded and recorded.
- Warmups and measured runs are distinguishable in raw data.
- Baseline and TACVM use comparable resources.
